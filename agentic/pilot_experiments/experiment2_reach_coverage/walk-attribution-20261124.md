# 实验二后续 · 走不好该怪谁（2026-11-24）

> **适用范围（2026-11-24 晚补）**：下文所有 Kimodo 的结果都跑在**我们自己的封装**里（`NativeKimodoPolicy`：Kimodo policy 的画布，100 帧历史 + 50 帧未来、每次只生成 1.67 s；policy 的推理函数和关节转换；引导照文档重写；没有装官方 `kimodo` 包）。所以它们只说明“**我们的封装产出的参考在滑**”，不能说明“Kimodo 不会走”。为分清这一点做的补充检查见文末“补充：是 Kimodo 还是我们的封装”。

**结论先说（11-25 再修订）：按官方方式整段生成后，SONIC 在仿真里走出向前 57%、侧步 47–48%、后退 42%、转身 96%（原来 13%、0%、−19%、50%），和它跟干净动捕的水平一样；见文末“修封装”。以下是 11-24 晚的结论：向前、侧步、后退走不出来，是我们的封装把 Kimodo 用坏了，不是 Kimodo 底座。** 用 NVIDIA 官方流程、同一份权重、只给文字生成的走路，脚滑和步长和干净动捕相当，SONIC 回放走出 29–52%、转身 95%，和干净动捕的 42–61%、100% 相当。把官方设置逐项换成我们封装的做法，弄坏步态的是“每次都垫 100 帧历史、只生成后 50 帧”。SONIC 自己的短板仍在：后退拿干净参考也不到一半。

下面第一部分是白天按原计划做的三个测试，结论措辞已按这个范围改过；“补充”一节是晚上做的官方流程对照。

- 在仿真里实际跑时（Kimodo 每 0.5 s 从实测位置重新规划，SONIC 执行），Kimodo 发出的参考**腿部动作本身**只“走”出指令距离的 20%（向前），侧步和后退几乎为零（−13% 到 +8%）；SONIC 把腿部给的这一点执行了六到九成。

## 测试一 · 只测 SONIC

### 参考从哪来

- **Arena SONIC 示教**（HF `WilliamWang16/HumanoidArena_dataset_v3_1@ca04c2d5`，八个任务各 100 段，只下了动作表）。里面向前的段很多，后退、侧步、转身也都有（主要在 sit_sofa、open_door、football、boxing 里），所以没用 Kimodo 凑数。
- **LAFAN1 动捕重定向到 G1**（HF `lvhaidong/LAFAN1_Retargeting_Dataset` 的 `g1/walk*.csv`，30 Hz 重采样到 50 Hz）。加它是因为下一条。
- 选段（`walk_attribution.py mine`）：在参考自己的根部轨迹上找 2–4 s、方向单一的窗口（向前 / 后退 / 左 / 右要求偏离方向 < 14°、偏航 < 20°；转身要求转 ≥ 60° 且移动 < 0.2 m），根部高度一直高于 0.6 m（排除坐下），窗口前至少有 3.4 s 可作 Kimodo 的 100 帧历史。每段只取一个窗口，任务轮流取。

**Arena 示教的参考本身脚就在滑。** 按运动学（我的正运动学和训练用解码器逐帧一致，差 < 0.001 cm）算，站立脚平均滑 0.18–0.26 m/s，六到七成时间两只脚同时在动，参考根部走的距离里只有 34–59% 是腿真正“迈”出来的；Kimodo 自己的触地检测在这些段上也只把 20–60% 的帧算作触地。它是遥操作数据，帧时序还有抖动（每隔约 0.7 s 重复一帧、下一帧补双步）。所以下面把“按参考腿部可实现距离算的完成比例”也列出来，并以 LAFAN1 作为“干净步态”的基准。

### 怎么跑

- 起点和实验二相同：pp_box 房间的空地 (-4, -4)，面朝 +x，同一套对齐执行器，落地站稳后开始。

回答测试二的两个问题：

- **在我们的封装里**，走路方向（前、后、左、右）不存在接近基准的用法。 最干净的“整段”比正式设置只好一点（滑 0.28–0.36 对 0.35–0.43），离 LAFAN1（0.07–0.12）差三四倍，两脚同时动 69–77% 对 3–37%，步长只有动捕的三分之一到一半。连遥操作示教那种本身就滑的参考（0.18–0.26）都没赶上。
- **影响最大的因素是历史，而且方向和直觉相反**：给真实走路历史（不管是动捕还是示教）脚滑翻倍、两脚同时动升到九成以上；只给一帧历史时根部被拉着一路冲（完成 2.4–2.8 倍）。引导强度 4 也明显变差。文字、稀疏路点、步速几乎没有作用。不给根部约束、只给文字时，Kimodo 基本站着不动（和实验一会话看到的一样）。

## 交叉验证 · 把最干净的用法放进仿真

- 选法（看仿真结果之前定的）：四个走路方向都真在走（根部完成 ≥ 0.5）的用法里，四个方向平均脚滑最低的两种，即“整段”（0.32）和“示教步速”（0.34），和正式设置（0.39）并排。转身另外加跑了“一帧历史”（测试二里转身最好的用法）。

- 侧步和后退时，机器人每次都往前漂 13–29 cm（4 s 内），和实验二一样。测试一用干净参考时没有这个漂移，所以**往前漂来自 Kimodo 的参考**，不是 SONIC。

### 转身

- SONIC 可以排除：干净参考完成 100%（8 次）；执行 Kimodo 参考的转角 93–100%（四种用法各 5 次，机器人 46–59%，参考 47–62%）。
- Kimodo 生成得出干净的转身步态（“整段”和“一帧历史”，测试二），完美跟踪下“一帧历史”还几乎转足（98%）。但放进闭环后，参考自己只转了指令的 47–62%，四种用法之间没有大差别（正式 50%，一帧历史 58%，整段 59%，5 次一组，范围重叠）。
- 按判定线：第二条要求最好用法步态明显差于基准，不成立；第三条要求交叉验证明显上升，50% → 58–59% 不算大差别。所以转身形式上也是**分不清**，但范围已经缩到“闭环里怎么用 Kimodo”和 Kimodo 本身之间。
- 没验证的推测：每次规划的朝向条件从**实测**朝向起算，机器人比参考慢一点，新一段就从落后的朝向重新开始，转速被一次次打折（完美跟踪下没有这个落差，所以离线能转足）。要分清，把朝向条件改成从上一段参考的朝向起算（或一次给出整段转角）再跑 5 次。

## 按预定判定线逐条

判定线是开跑前定的，没有改：

1. **好参考在某方向完成不到一半 → 这个方向归 SONIC。** 后退：LAFAN1 42%（8 次）、示教 26%（8 次），两套参考都不到一半 → **后退归 SONIC**。示教参考的侧步（左 32%、右 5%）也不到一半，但干净参考（61%、54%）过了一半，侧步不按这条落格。
2. **好参考 ≥ 80%，且 Kimodo 最好用法步态仍明显差于基准 → 归 Kimodo 底座。** 只有转身的 SONIC 过了 80%（100%），但转身的最好用法步态已经接近基准，这条不成立。向前（63%）、侧步（54–61%）不到 80%，这条形式上不适用。
3. **换用法后步态接近基准，且交叉验证里完成比例明显上升 → 归用法。** 走路方向没有用法接近基准，不成立；转身见上一节。
4. **落在中间的写“分不清”。** 转身见上一节。向前和侧步：SONIC 拿好参考在 50%–80% 之间，Kimodo 怎么用都远离基准，交叉验证没有上升。形式上分不清。还缺的测试：让 SONIC 在**和 Kimodo 相同的条件**下（从站姿起步、0.35 m/s、闭环重规划）跟一段干净参考，看能否到 80%；或者给 Kimodo 一个落脚点约束，看腿部给出的距离能不能从两成升上去。

不按判定线、只看拆解：向前和侧步的损失大头在我们的封装产出的参考的腿（只给出两成到零），SONIC 再丢一到四成。这是 Kimodo 底座还是我们的封装造成的，见文末补充。

## 下一步建议（按证据强弱排）

0. **（晚上补充后，优先级最高）改封装，不要垫 100 帧历史再只生成 50 帧。** 官方流程整段生成就是干净的（见文末补充）。下一步要做的是在闭环里用接近官方的方式：例如每次整段生成几秒、只用少量帧或只用根部状态接续，而不是 100 帧全身历史；先在离线完美跟踪下量步态，再进仿真。
1. **（白天的建议，已被第 0 条取代）在我们的封装下，走路不要让 Kimodo 管腿**（18 种用法，仿真里腿部只给出 0–20%）。后续的动捕步幅试验见文末：方向对了，但没过判定线。上身交给 Kimodo（伸手、前倾，实验二里髋带动的前倾已能做到），腿另找来源。最省事的不训练做法：用 LAFAN1 这种干净动捕片段按方向拼腿部参考（SONIC 已经能把它们走出 54–63%，转身 100%），外面按实测位置闭环选片段。需要：片段库和过渡、上下身拼接（腰以上用 Kimodo，腰以下用片段）、闭环规则；先在向前和侧步上验证。
2. **后退不靠 SONIC**（证据：两套好参考都不到一半）。短期在任务设计上避开纯后退（转身 + 向前），长期要能接受根部速度指令的执行器。
3. **转身先只改用法**（SONIC 已排除）：朝向条件从参考而不是实测起算，或一次给出整段转角；5 次就能看出能否从 50–59% 升到 80% 以上。如果升不上去，再归到 Kimodo 底座。
4. **换或自己训 tracker**：只有在第 1 条做完后向前、侧步仍到不了 80% 时才值得。要看的是它能否接受根部位置或速度指令（Arena 的 SONIC 没有这个输入），以及后退的完成比例。自己训需要的数据：Arena 示教（每任务 100 段）加 LAFAN1，奖励里要有根部速度跟踪。

## 这些数字的边界

- 样本少：测试一每格 4–8 次，测试二和交叉验证每格 5 次，只认大差别。侧步、后退的完成比例分布很宽（如示教后退 −61% 到 58%）。
- 测试一是开环回放，参考速度是录制的速度（LAFAN1 0.41–0.58 m/s，示教 0.13–0.40 m/s），起步前还有 3.4–5 s 的引导段；交叉验证是从站姿起步、0.35 m/s、闭环。两者不是同一条件，所以没有直接拿测试一的比例去套交叉验证。
- “腿部给出的距离”是运动学估计：两只脚都着地时取平均，没有区分哪只脚在发力。
- 测试二的引导：带文字时用的是分离式 CFG（无条件、只有约束、只有文字三次前向），这是按 Kimodo 文档实现的，没有和原始 Kimodo 代码逐数核对。
- 测试二的起点和起步历史来自实验二的一次运行；“一帧历史”在实验二的设置里本来就接近（起步时只有约 18 帧站立）。
- 没做：落脚点约束、更长的生成段（> 1.6 s）、Kimodo 训练时的原生方式（带图像的 VLA 规划器），以及 SONIC 在 Kimodo 同条件下跟干净参考（见上文“还缺的测试”）。

## 补充：是 Kimodo 还是我们的封装（2026-11-24 晚）

用户指出官方 Kimodo 的生成质量应该很好，Kimodo policy 用它也走得很好。上面 18 种用法全跑在同一个封装里，所以补了下面几项。

### 1. 特征 ↔ 关节的转换会不会自己造出脚滑：不会

- 做法（`walk_attribution.py roundtrip`）：把测试一的 33 段 LAFAN1 窗口编码成 Kimodo 的 417 维特征，再按发给 SONIC 的同一条路径解回（逆变换 → 50 Hz 插值 → 编码成动作 → 关节限位和速度约束），用同一把尺子量。
- 结果（站立脚滑动 m/s / 两脚同时动 / 步长 m，中位数）：

| 方向 | 段数 | 原始动捕 | 只重采样 | 经过特征再编码 | 再加关节限位和速度约束 | 特征里由旋转算脚 | 特征里由位置算脚 |
|---|---:|---|---|---|---|---|---|
| 向前 | 8 | 0.110 / 6% / 0.88 | 0.110 / 7% / 0.88 | 0.110 / 7% / 0.88 | 0.123 / 8% / 0.88 | 0.082 / 7% / 0.88 | 0.082 / 7% / 0.88 |
| 后退 | 8 | 0.120 / 14% / 0.62 | 0.129 / 14% / 0.62 | 0.129 / 14% / 0.62 | 0.148 / 19% / 0.62 | 0.109 / 14% / 0.62 | 0.109 / 14% / 0.62 |
| 左 | 5 | 0.070 / 3% / 0.69 | 0.070 / 2% / 0.69 | 0.070 / 2% / 0.69 | 0.070 / 2% / 0.67 | 0.071 / 3% / 0.70 | 0.071 / 3% / 0.70 |
| 右 | 4 | 0.098 / 37% / 0.92 | 0.098 / 37% / 0.92 | 0.098 / 37% / 0.92 | 0.100 / 38% / 0.92 | 0.097 / 38% / 0.92 | 0.097 / 38% / 0.92 |
| 转身 | 8 | 0.120 / 30% / 0.36 | 0.120 / 29% / 0.36 | 0.120 / 29% / 0.36 | 0.126 / 29% / 0.34 | 0.124 / 29% / 0.36 | 0.124 / 29% / 0.36 |

（特征那两列是 30 Hz，其余 50 Hz。）

- 对 Kimodo 自己的输出：交叉验证正式设置那 25 次运行保存的 250 次规划，脚由旋转重建和由位置特征重建，站立脚滑动 0.288 对 0.287 m/s、两脚同时动 74% 对 74%，一样。
- 结论：转换回路不制造脚滑（限位和速度约束最多加 0.01–0.03 m/s）。之前所有脚滑数字都是生成出来的运动本身的，但只是**我们的封装驱动 Kimodo**时生成的。

### 2. 官方用法和我们的封装逐项对照

来源：官方代码 [nv-tlabs/kimodo](https://github.com/nv-tlabs/kimodo)（提交 `e1c219c`）的 `kimodo/scripts/generate.py`、`kimodo/model/kimodo_model.py`、`kimodo/model/cfg.py`、`kimodo/exports/mujoco.py`；模型卡 [nvidia/Kimodo-G1-RP-v1](https://huggingface.co/nvidia/Kimodo-G1-RP-v1)；权重自带的 `config.yaml`（`cfg_type: separated`，`fps: 30`，`input_first_heading_angle: true`，`num_text_tokens_override: 50`）。

| 项 | 官方 | 我们的封装 |
|---|---|---|
| 一次生成多少 | 整段，命令行默认 5 s = 150 帧（30 fps），从零开始 | 100 帧历史 + 50 帧未来（1.67 s），执行 0.5 s 后重新生成 |
| 历史 | 没有（多句拼接时用 5 帧过渡） | 最多 100 帧已发出的参考，当作观测运动 |
| 文字 | LLM2Vec（McGill mntp + supervised） | 同一个编码器；但默认设置把文字置零 |
| 引导 | 分离式，文字 2.0 / 约束 2.0（三次前向：只有文字、只有约束、都没有） | 默认只对约束引导 2.0，它的“无条件”那次连历史也去掉；加文字时按官方公式重写 |
| 约束 | 可选：根部二维路径、末端执行器、关键帧，用官方的约束类生成观测和掩码 | 逐帧根部路径 + 朝向，直接写进特征掩码 |
| 扩散步数 / 采样器 | 100（命令行默认）/ DDIM | 50 / DDIM |
| 起始朝向 | 显式输入（默认 0） | 从历史里推 |
| 后处理（防脚滑） | **官方脚本对 G1 关掉**（注释：对这个模型效果不好） | 没有 |
| G1 关节角导出 | 官方 `MujocoQposConverter` | 我们的编码 + 关节限位和速度约束（第 1 项显示不额外制造脚滑） |

最可疑的两项：每 0.5 s 重新生成一段 1.67 s、而且垫着 100 帧历史；只对约束引导时，“无条件”那一路连历史也去掉。

### 3. 官方流程生成：和动捕一样干净

- 做法（`official_kimodo.py`）：官方代码 [nv-tlabs/kimodo](https://github.com/nv-tlabs/kimodo) `e1c219c`，装在开发机独立的虚拟环境里（继承策略环境的包，另装了 `gradio_client`、`scenepic`、`bvhio`、`boto3`，`huggingface_hub` 降到 1.0 以下；没动现有环境）。同一份 `Kimodo-G1-RP-v1` 权重，官方加载器、官方生成调用（和官方 `generate.py` 一样：多句模式、5 帧过渡、`num_samples=1`、不加后处理）、官方 G1 导出（`MujocoQposConverter`），100 步，只给文字，5 个方向 × 5 个种子 × 8 s。量的窗口去掉开头 1 s（从静止起步）。
- 唯一的替换：官方文字编码器要用 Llama-3 底座（要申请权限），通过官方加载器的 `text_encoder` 参数换成返回现成短语向量的替身（同一个 LLM2Vec 编码器，形状按官方编码器的输出 `[B, 1, 4096]`）。用户同意后才运行（第一次启动被权限检查拦下）。
- 官方 G1 脚本本来就不加后处理，所以“只有加后处理才干净”这一条不适用。

结果（站立脚滑动 m/s / 两脚同时动 / 步长 m，每格 5 次的中位数）：

| 方向 | 官方流程 | LAFAN1 基准 | 我们的封装“正式” | 我们的封装“整段” |
|---|---|---|---|---|
| 向前 | 0.127 / 23% / 1.22（0.89 m/s） | 0.110 / 6% / 0.88 | 0.35 / 80% / 0.25 | 0.28 / 77% / 0.36 |
| 后退 | 0.131 / 8% / 1.03 | 0.120 / 14% / 0.62 | 0.43 / 79% / 0.21 | 0.36 / 70% / 0.47 |
| 左 | 0.064 / 12% / 0.90 | 0.070 / 3% / 0.69 | 0.41 / 81% / 0.23 | 0.32 / 74% / 0.38 |
| 右 | 0.050 / 3% / 0.69 | 0.098 / 37% / 0.92 | 0.38 / 76% / 0.22 | 0.31 / 69% / 0.16 |
| 转身 | 0.033 / 0% / 0.21（转 89–96°） | 0.120 / 30% / 0.36 | 0.26 / 58% | 0.15 / 29% |

### 按用户给的判读规则

- 官方流程的脚滑和步长接近 LAFAN1 基准（上表），SONIC 回放的完成比例接近测试一里 LAFAN1 的水平 → 按规则第一条：**问题在我们的封装**，不是 Kimodo 底座。之前“底座本身生成不出干净迈步”的说法不成立，撤回。
- 最可疑的一项（第 5 项定位）：**每次生成都垫着 100 帧历史、只生成后面 50 帧**。这是 Kimodo policy（VLA）的用法，也是我们封装照搬的画布；冻结的 Kimodo 底座在这种用法下步态坏掉（两脚同时动 34–70%，转身完全不转）。扩散步数、逐帧根部路径、文字权重 0、关节转换都已排除。
- 转换回路（第 1 项）没有制造脚滑，之前所有脚滑数字有效，但只描述我们封装的输出。
